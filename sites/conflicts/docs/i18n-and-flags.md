# Languages and flags

## Adding a language

Two steps, nothing else:

1. Create `src/i18n/locales/<code>.ts` exporting a `Messages` object.
2. Register it in `LOCALES` in `src/i18n/index.ts`.

The switcher, detection and persistence pick it up automatically.

`Messages` (`src/i18n/types.ts`) is a **typed nested object, not a `t('some.key')` lookup**. That
is the enforcement mechanism: an incomplete translation fails to compile instead of leaking
`some.key` into the interface at runtime. Keep it that way — do not add a string-key fallback.

Locale resolution: `localStorage` → `navigator.languages` (matched on the primary subtag, so
`de-AT` gets German) → `en`. The choice is persisted and stamps `document.documentElement.lang`.

## Formatting

Never format a number inline. `src/i18n/format.ts` wraps `Intl`:

| | en | de |
|---|---|---|
| `formatDeaths` | `75M`, `620k` | `75 Mio.`, `620 Tsd.` |
| `formatShare` | `3.1%` | `3,1 %` |
| grouping | `2,394` | `2.394` |

Suffixes come from `Messages.units`, separators from `Intl` — neither is baked into call sites.

## Translating data

`data/curated/i18n/<locale>.yaml`, keyed by conflict id:

```yaml
world-war-ii:
  name: Zweiter Weltkrieg
  region: Weltweit
  sides: [Alliierte, Achsenmächte]     # same order as the source `sides`
  summary: >
    …
```

Every field is optional and **falls back per field**, so a half-finished language shows
translated titles above English prose rather than blanks. `localized()`, `localizedSide()` and
`localizedMembers()` in `src/data/conflicts.ts` do the resolution. `npm run data:conflicts`
reports coverage, and `npm run data:validate` checks it per field:

```
i18n/de.yaml                105 of 105 (100%)
```

Belligerent member names are translated through a single dictionary,
`data/curated/i18n/names.de.yaml` (`English name: German name`), which the compile step bakes
into per-conflict arrays — never hand-write a `members` list in `de.yaml`. The same dictionary
feeds the German polity names for the map hover card (`public/data/borders/names.de.json`,
generated by `npm run data:flags`). The English names stay the join key everywhere in code
(flags, involvement matching); translations only ever reach JSX.

Battle names (the ~6,500 Wikidata dots) are translated from **Wikidata's own labels**: the
battles pipeline fetches each configured locale's `rdfs:label` in the same queries as the
English one and writes a sparse `battles.names.<locale>.json` (battle index → name, only where
a label exists and differs from English — ~1,960 entries / 21 KB gzipped for German). The app
fetches the overlay lazily — only in a non-English locale, and only once the battle layer is
actually on screen (`syncNames()` in `src/data/battles.ts`) — and falls back to English per
battle, like every other field. To cover a new language, add its code to `LABEL_LOCALES` in
`pipeline/3-wikidata-battles.ts` and re-run `npm run data:battles`; the overlay and
`battles.json` must come from the same run, or the index keys desync.

Search matches both the English original and the active translation — a German reader finds
"Zweiter Weltkrieg" while someone typing "World War" still gets a hit, which matters because
English names are what external references use.

German currently ships complete but was translated without a native reviewer. Historical
terminology follows standard German usage (*Dreißigjähriger Krieg*, not a literal rendering).
Any side or member name containing a comma must be double-quoted in the YAML flow sequence —
an unquoted comma splits the entry and shifts every following label onto the wrong belligerent.
The validator errors on the resulting count mismatch.

## Flags

`npm run data:flags` resolves polity names to ISO 3166-1 alpha-2 codes and copies only the needed
SVGs from `flag-icons` into `public/data/flags/` (174 files, ~1.6 MB total, ~170 bytes gzipped
each, fetched one at a time on hover).

### SVG, not emoji

Regional-indicator emoji (🇩🇪) are the obvious cheap answer and they do not work: **Windows ships
no country-flag glyphs**, so Chrome and Edge on Windows render the letter pair "DE" in a box. Do
not "simplify" this to emoji.

### The mapping

Most of it is *generated* from `Intl.DisplayNames` in English and German, so every modern state is
covered for free and cannot drift. Only two hand-written pieces exist in `pipeline/5-flags.ts`:

- `HISTORICAL` — genuine successors: Ottoman Empire → TR, Ceylon → LK, Siam → TH, Manchu Empire → CN.
- `BLOCKED` — refused even if fuzzy matching would find them: Prussia, Korea, Congo, Yugoslavia,
  Czechoslovakia, Georgia, the Holy Roman Empire, every pre-national empire.

**Only ~7% of the 2,837 polity names get a flag, and that is the correct outcome, not a gap to
close.** Most names are historical states with no modern successor ("Great Khanate") or
ethnographic groupings ("Savanna hunter-gatherers"). A modern flag on a medieval khanate is an
invention; no flag is the honest answer. The About panel states this in both languages.

### The trap

`Intl.DisplayNames` still answers for **deprecated and reserved codes**, and they sort *after* the
live ones. A naive AA–ZZ loop with last-writer-wins maps:

| name | wrong | right |
|---|---|---|
| France | FX (Metropolitan France) | FR |
| United Kingdom | UK (reserved) | GB |
| Russia | SU (Soviet Union) | RU |
| Serbia | YU (Yugoslavia) | RS |

None of those have flag assets, so the failure surfaces as *"France has no flag"* rather than as
an error — and the overall coverage percentage barely moves, so it hides. `displayNameMap`
filters to codes that actually ship an asset and takes the **first** writer.

If you extend the mapping, verify by looking up specific well-known countries, not by watching the
coverage number.
